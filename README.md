# Тестовое задание: тестирование Shop API

**Позиция:** джуниор-тестировщик
**Время:** 1 рабочий день (ориентир 6–8 часов)
**Обязательные инструменты:** [Claude Code](https://claude.com/claude-code), Git, Docker Desktop

---

## Что нужно сделать

Вы получили REST API интернет-магазина: товары, склады, остатки и продажи. Протестируйте его **методом чёрного ящика** и подготовьте три документа: тест-план, тест-дизайн и отчёт о тестировании.

Работать нужно **через Claude Code**: от клонирования и развёртывания до выполнения проверок. Claude Code — ваш инструмент, но за результат отвечаете вы. Всё, что он сгенерировал, нужно проверить и понимать.

### Шаг 1. Получить проект

Из Claude Code склонируйте репозиторий:

```
https://github.com/avitvinov/TestApi.git
```

После клонирования **перейдите в папку проекта и запустите Claude Code из неё**. Тогда он подхватит правила проекта из `CLAUDE.md`.

### Шаг 2. Развернуть API в локальном Docker

Соберите и запустите контейнер с помощью Claude Code (в проекте есть `Dockerfile` и `docker-compose.yml`). API должно отвечать на `http://localhost:3000`.

Если что-то не запускается, разберитесь, в чём причина. Опишите проблему и её решение в отчёте: это тоже часть задания.

### Шаг 3. Изучить протокол

Документация API (Swagger UI): **http://localhost:3000/docs**

Это **единственный источник требований**. Ожидаемое поведение API описано там: правила валидации, коды ответов, бизнес-правила, авторизация. Ожидаемые результаты в тест-кейсах берите только из неё.

> Все методы `/api/*` требуют подписи запроса. Как её сформировать, описано в разделе «Авторизация» в Swagger. Разобраться с подписью — часть задания.

### Шаг 4. Тест-план

Подготовьте `qa/test-plan.md`. Минимальная структура:

1. **Объект тестирования:** что тестируем, версия, окружение.
2. **Область тестирования:** что входит, что **не** входит и почему.
3. **Подход:** виды тестирования, техники тест-дизайна, инструменты.
4. **Окружение:** как развёрнуто, ОС, версии Docker и браузера.
5. **Критерии начала и окончания тестирования.**
6. **Риски** и что с ними делать.
7. **Оценка трудозатрат** по этапам.

### Шаг 5. Тест-дизайн

Подготовьте `qa/test-design.md` (или `.xlsx`/`.csv`, если удобнее в таблице).

- Для каждого метода API выпишите проверки. Покажите, какие **техники** вы применили: классы эквивалентности, граничные значения, таблица решений, переходы состояний, негативное тестирование и т.д.
- Оформите тест-кейсы. У каждого: ID, название, предусловия, шаги (метод, URL, тело), ожидаемый результат **со ссылкой на пункт документации**, приоритет.
- Добавьте **матрицу трассировки**: какое требование из Swagger покрыто какими тест-кейсами.

### Шаг 6. Выполнение тестов

Выполните тест-кейсы. Делать это можно через Claude Code (curl, скрипты), Swagger UI («Try it out»), Postman — как удобнее. Для каждого кейса зафиксируйте фактический результат и статус: Passed, Failed или Blocked.

Автотесты не обязательны, но будут плюсом. Если они есть, положите их в `qa/autotests/` и опишите, как их запустить.

### Шаг 7. Отчёт о тестировании

Подготовьте `qa/test-report.md`:

1. **Краткое резюме:** готово ли API к релизу, на ваш взгляд, и почему.
2. **Что протестировано:** окружение, период, сколько кейсов выполнено, сколько из них Passed, Failed и Blocked.
3. **Непройденные кейсы (Failed):** сводная таблица и подробное описание каждого (в отчёте или отдельными файлами в `qa/failed/`): заголовок, шаги воспроизведения, ожидаемый результат (со ссылкой на документацию), фактический результат (код и тело ответа), серьёзность, приоритет.
4. **Проблемы при развёртывании** и как вы их решили.
5. **Рекомендации.**

### Шаг 8. Журнал работы с Claude Code

Приложите `qa/ai-log.md`: 5–10 ключевых запросов (промптов), которые вы давали Claude Code, и для каждого коротко:
- что получили в ответ;
- что пришлось исправить или перепроверить;
- где Claude Code ошибся, если такое было.

## Правила

1. **Чёрный ящик.** Исходный код в репозитории нужен только для сборки контейнера. **Читать** `server.js`, `docs.js` и `public/` **запрещено** и вам, и Claude Code. Требования берите только из Swagger, поведение проверяйте только через HTTP.
2. Не меняйте исходный код и правила проекта (`CLAUDE.md`, `.claude/`).
3. Описание непройденного кейса, которое ссылается на строки кода, а не на документацию и фактический ответ API, засчитано не будет.
4. Данные хранятся в памяти. `POST /api/reset` возвращает исходное состояние, перезапуск контейнера тоже.

## Как сдать

Заархивируйте папку `qa/` и отправьте её проверяющему. **Не делайте push** в этот репозиторий и не публикуйте свои результаты в открытом доступе.

## Как оценивается

- тест-план: полнота, реалистичность, понимание рисков;
- тест-дизайн: применение техник, покрытие требований, качество тест-кейсов;
- отчёт: результаты прогона, качество описания непройденных кейсов, обоснованность выводов;
- работа с Claude Code: умение ставить задачи, критически проверять ответы, не принимать выводы модели на веру.
